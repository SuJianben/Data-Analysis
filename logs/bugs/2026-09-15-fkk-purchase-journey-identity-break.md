# 2026-09-15 FKK 购买前行为与订单身份断链

## 缺陷

- FKK 用户行为列表中一笔真实购买只显示 1 条 `purchase`，没有购买前页面、点击、加购或结账轨迹。
- 面板把带客户哈希的订单事件显示为“登录客户”，但 Shopify 访客可能以游客身份下单，文案含义不准确。

## 复现与证据

- 已用订单哈希、客户哈希、金额、币种、商品数量和时间核对该购买，确认它对应 Shopify 真实有效订单。
- 异常购买使用 `visitor_shopify_<事件标识>` 兜底访客号，事件数、页面数和购买数均为 1。
- 同期另一笔正常购买沿用主题访客号，与 14 条购买前点击归并为同一客户轨迹。
- 代码检查确认旧 Pixel 依赖结账页面读取主题写入的 localStorage/sessionStorage；读取失败时会生成新的兜底访客号。
- 主题登录态使用 HMAC-SHA-256，Customer Pixel 使用普通 SHA-256，存在第二条身份不一致路径。

## 根因

- 购买归并依赖跨页面读取主题存储，而该存储在部分结账链路中不可用。
- Worker 只会把相同 `visitor_id` 下的购买客户哈希反向归到购买前行为；兜底号与主题访客号不同，因此无法归并。
- 主题与 Pixel 没有使用同一个权威身份来源。

## 修复方案

- FKK 主题点击只通过 `Shopify.analytics.publish` 发布自定义事件。
- FKK Customer Pixel 统一订阅页面、点击、加购、开始结账和完成购买，并以 Shopify `clientId` 生成访客标识。
- 客户和订单统一在 Pixel 中使用 SHA-256；主题不再计算或发送客户哈希。
- 每条新 Signal 事件写入 `identitySource`，区分 `shopify_client_id` 与 `shopify_event_fallback`。
- 数据健康新增“购买轨迹归并”，统计已串联购买和兜底购买。
- 面板“登录客户”改为“已识别客户”，避免把游客订单误称为登录用户。

## 验证

- Customer Pixel 模拟完整链路通过：页面、点击、加购、开始结账、购买共用一个 Shopify clientId。
- 原始客户 ID 和订单 ID 未进入 Signal 载荷，客户与订单哈希均为 64 位。
- Worker 隔离来源校验通过；站点冒充、身份来源不一致和无元素语义点击被拒绝。
- 旧版购买只在使用旧访客格式且没有 `identitySource` 时兼容；新版购买身份来源不一致时线上返回 403。
- 线上 Worker 正向写入返回 200，D1 回读身份来源正确；反向请求返回 403。
- 线上测试记录已按站点、来源、事件 ID 和访客 ID 精确删除，复查剩余 0 条。
- 数据健康线上已显示：最近7天 2 次购买，1 次已串联、1 次使用兜底身份。

## 状态
